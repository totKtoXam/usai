# V1 Implementation Plan

## Target

V1 должен дать рабочий deterministic CLI:

```bash
usai init
usai prompt application-usecase
usai rules sources list
usai rules list
usai rules search clean
usai rules install clean-code --size nano --target always
usai rules update
```

## Stack

```text
Language: TypeScript
Runtime: Node.js
CLI framework: commander or cac
Interactive prompts: @clack/prompts or @inquirer/prompts
Config validation: zod
YAML/frontmatter: yaml + gray-matter
Templates: small custom renderer first, avoid complex DSL
Markdown tooling: prettier/remark later, not required for first MVP
Tests: vitest or node:test + golden files
Build: tsup or esbuild
Package manager: pnpm
```

Recommendation: start with a small custom renderer for `{{...}}` placeholders. Add a full template engine only if simple replacement becomes insufficient.

  - `dev`

```text
src/

    prompt/
    rules/

    templates/
    fs/

tests/

  golden/
```

### Done When

- `pnpm build` succeeds.
- `usai --help` runs locally.
- One smoke test executes the CLI entrypoint.

## Phase 2: Prompt Generation MVP

### Tasks

- Implement template lookup by name.
- Implement mode detection:
  - simple
  - structured
  - extended
- Implement Simple Mode parser:
  - `{{ Question text? }}`
  - `{{key: Question text?}}`
  - `{{key:type: Question text?}}`
  - `{{key:select(option1,option2): Question text?}}`
  - `{{key}}`
- Implement question model:
  - `text`
  - `textarea`
  - `select`
  - `file`
  - `text[]`
  - `file[]`
  - `select[]`
  - `boolean`
  - `number`
- Implement answers file support for non-interactive tests.
- Implement markdown rendering for scalar and list values.
- Implement output file generation.

### Tests

- Parser unit tests for every placeholder form.
- Golden tests for simple templates.
- Integration test for `usai prompt application-usecase --answers answers.yaml --no-interactive`.

### Done When

- Developer can create a useful prompt template as one `.md` file.
- The CLI can render exact generated markdown from fixture answers.
- Duplicate placeholders ask once and reuse answers.

## Phase 3: Structured And Extended Templates

### Tasks

- Implement YAML frontmatter parsing for Structured Mode.
- Implement external schema loading for Extended Mode.
- Implement required/default validation.
- Implement output filename metadata.
- Add structured and extended sample templates behind `usai init --with-samples`.

### Tests

- Golden tests for structured templates.
- Golden tests for extended templates.
- Validation tests for required/default fields.
- Error tests for missing external schema.

### Done When

- All three template modes compile to the same internal `TemplateDefinition`.
- Simple Mode remains the default recommended path.

## Phase 4: Config Resolution

### Tasks

- Implement built-in defaults.
- Implement global config path resolver.
- Implement project `.usai/config.json` loader.
- Implement config merge priority:

```text
CLI flags
-> project config
-> global config
-> built-in defaults
```

- Validate config with zod.
- Add exact error messages for invalid config fields.

### Tests

- Unit tests for merge order.
- OS path resolver tests with injected platform.
- Integration tests for project/global override scenarios.

### Done When

- CLI works without global config.
- Project config can override paths and default source.
- CLI flags override config values.

## Phase 5: Local Rules Sources

### Tasks

- Implement rules source model.
- Implement `rules sources list`.
- Implement `rules sources add`.
- Implement `rules sources remove`.
- Implement `rules sources set-default`.
- Implement local source catalog builder.
- Implement `rules list --source <name>`.
- Implement `rules search <query> --source <name>`.
- Implement `rules install <rule-name> --size <size> --target <target> --source <name>`.

### Tests

- Unit tests for source config validation.
- Catalog builder tests from local fixtures.
- Integration tests for install/search/list against local source fixture.
- Overwrite protection tests.

### Done When

- Full rules workflow works offline with local fixture source.
- Installed rules land in `docs/rulesets/<target>/`.
- Existing project rules are not overwritten silently.

## Phase 6: GitHub Source And agent-rules-books

### Tasks

- Implement source cache directory abstraction.
- Implement `rules update` for source cache.
- Implement public GitHub source download.
- Add built-in `agent-rules-books` source.
- Implement `rules list/search/install` against cached GitHub source.
- Add optional smoke test against real `agent-rules-books`.

### Tests

- Unit tests for cache path resolution.
- Integration tests using mocked GitHub/download source.
- Optional network smoke test for `agent-rules-books`.
- Test that `rules update` never rewrites project rulesets.

### Done When

- `usai rules update --source agent-rules-books` refreshes cache.
- `usai rules install clean-code --size nano --target always` works from default source.
- Network logic is isolated from rules parsing/install logic.

## Phase 7: Packaging And Release Hardening

- Add install docs.
- Add GitHub Actions:

  - test
  - lint

- Add manual smoke checklist for Windows/Linux/macOS.
- Investigate standalone binary packaging path, but do not block v1 on it.

### Tests

- Build artifact smoke test.
- Installed package smoke test.
- CLI help snapshot.

### Done When

- `usai` can be installed globally through the initial package channel.
- Release artifact is documented.
- V1 commands pass tests and manual smoke checklist.

## V1 Cut Line

Do not include in V1:

- export adapters;
- handoff generator;
- metrics;
- plugin system;
- private source auth;
- rules dependency resolution;
- complex template conditions/loops;
- AI calls.
