# V1 Test Plan

## Scope

V1 покрывает deterministic project setup, prompt generation, config resolution and rules management.

Commands:

```bash
usai init
usai prompt <template-name>
usai rules sources list|add|remove|set-default
usai rules list
usai rules search <query>
usai rules install <rule-name> --size <nano|mini|full> --target <target>
usai rules update
```

## Project Initialization

### Unit Tests

- Scaffold manifest contains only expected files and directories.
- Default project config matches documented paths.
- Existing file conflict detection returns correct status.

### Integration Tests

- `usai init` creates `.usai/config.json`, `AGENTS.md`, `docs/devs`, `docs/rulesets`, `docs/decisions`.
- `usai init` creates `docs/devs/ai-workflows/modules`.
- `usai init` initializes the current directory and does not walk up to a parent `.git`.
- `usai init --root <path>` initializes the explicit target directory.
- Re-running `usai init` without `--force` does not rewrite existing files.
- `usai init --force` rewrites only files owned by the scaffold.
- `usai init --minimal` creates config and required directories without sample-heavy content.
- `usai init --with-samples` creates simple, structured and extended prompt examples.
- Default scaffold creates `docs/devs/README.md`.
- Root `AGENTS.md` includes context-scope guard, `docs/devs` human-only rule and Docs Maintenance Gate.
- Project config includes `paths.aiWorkflows` and does not include legacy `generatedPrompts`/`handoffs` paths.
- `usai init --with-samples` creates workflow prompt templates for feature brief, slice prompts, slice implementation and review.
- Public docs contain `docs/user-guide/commands/init.md`.
- `CHANGELOG.md` has an `Unreleased` section.

### Acceptance Checks

- After `usai init`, `usai prompt application-usecase` works without separate YAML schema.
- Workflow artifacts use `docs/devs/ai-workflows`, not separate generated prompt and handoff directories.
- Root `AGENTS.md` is a router file and does not include all ruleset content.
- Default scaffold does not create `.gitkeep` placeholder files.
- README and user guide do not present planned commands as already available.

## Config Resolution

### Unit Tests

- Merge order is `CLI flags -> project config -> global config -> built-in defaults`.
- Project paths resolve relative to project root.
- Global config path resolves per OS convention.
- Built-in `agent-rules-books` is available when no config exists.
- `paths.aiWorkflows` resolves relative to project root.
- Invalid config reports exact field path.

### Integration Tests

- CLI works with project config only.
- CLI works with global config only.
- Project config overrides global default source.
- Project config can override `paths.aiWorkflows`.
- CLI `--source` overrides both project and global config.

### Acceptance Checks

- No test writes to a real user global config.
- Version field is required and invalid version fails clearly.

## Prompt Generation

Prompt generation tests are grouped by the three Phase 2 delivery subphases. Shared tests should live close to the reusable core model, while mode-specific tests should prove that each mode maps into the same renderer.

### Phase 2.1: Simple Mode

#### Unit Tests

- Template mode detection recognizes Simple Mode and rejects unimplemented modes clearly until later subphases are complete.
- Template reference resolution distinguishes reusable template names from direct markdown file paths.
- Simple Mode placeholders are parsed:
  - `{{ Question text? }}`
  - `{{key: Question text?}}`
  - `{{key:type: Question text?}}`
  - `{{key:select(option1,option2): Question text?}}`
  - `{{key}}`
- Duplicate keys produce one question and reuse the same answer.
- Placeholder key slugification is deterministic.
- List values render as markdown lists.
- Optional empty lists render as `none`.
- File values render as path strings and do not read file contents.

#### Golden Tests

- Simple template + answers file -> exact generated markdown.
- List answers render with stable ordering.
- Boolean and number answers render consistently.

#### Integration Tests

- `usai prompt application-usecase --answers answers.yaml --no-interactive` generates output without prompts.
- `usai prompt ./draft.md --answers answers.yaml --no-interactive --output ./final.md` renders a direct path template.
- `usai prompt application-usecase --output <path>` writes to explicit path.
- Missing required answer fails with non-zero exit code.
- Unknown template name fails with a helpful message and available templates.
- Existing output file asks for confirmation or requires `--force` in non-interactive mode.

#### Acceptance Checks

- A developer can create a new useful template as a single `.md` file.
- A workflow `draft.md` can be compiled into `final.md`.
- No AI call or network call happens during prompt generation.

### Phase 2.2: Structured Mode

#### Unit Tests

- Template mode detection recognizes frontmatter-based Structured Mode.
- Frontmatter questions map into the same internal prompt question model as Simple Mode.
- Required/default validation works for frontmatter-defined questions.
- Output directory and filename metadata are validated.
- Unsupported frontmatter fields fail with exact field paths.

#### Golden Tests

- Structured template with frontmatter -> exact generated markdown.
- Structured template defaults render without interactive input when answers are omitted.
- Structured template output filename is stable for the same answers.

#### Integration Tests

- `usai prompt <structured-template> --answers answers.yaml --no-interactive` generates output without prompts.
- Missing required frontmatter question fails clearly.
- Invalid frontmatter fails before asking any questions.

#### Acceptance Checks

- Structured Mode works as one `.md` file with metadata and questions in YAML frontmatter.
- Existing Simple Mode templates still render identically.

### Phase 2.3: Extended Mode

#### Unit Tests

- Template mode detection recognizes schema-backed Extended Mode.
- External schema loading resolves from configured prompt schema directory.
- External schema questions map into the same internal prompt question model as Simple and Structured modes.
- Required/default validation works for schema-defined questions.
- Schema/template placeholder mismatch fails clearly.

#### Golden Tests

- Extended template with external YAML schema -> exact generated markdown.
- Shared schema can be reused by more than one template fixture.
- Extended template output metadata is stable.

#### Integration Tests

- `usai prompt <extended-template> --answers answers.yaml --no-interactive` generates output without prompts.
- Missing external schema fails with a helpful message.
- Invalid external schema fails before asking any questions.

#### Acceptance Checks

- Extended Mode supports large reusable schemas.
- Existing Simple and Structured Mode templates still render identically.

## Rules Sources

### Unit Tests

- Effective default source resolution follows config priority.
- Source name validation rejects empty or duplicate names.
- `github` and `local` source configs validate correctly.
- Built-in source cannot be removed from built-in defaults, but default can be changed.

### Integration Tests

- `usai rules sources list` shows built-in source.
- `usai rules sources add company-rules <local-path>` updates config.
- `usai rules sources set-default company-rules` changes effective default.
- `usai rules sources remove company-rules` removes user-defined source.

### Acceptance Checks

- Every rules command accepts `--source <name>`.
- Without `--source`, commands use effective default source.

## Rules Discovery

### Unit Tests

- Catalog builder can infer rule names and sizes from file structure.
- Search matches by rule name, description and tags.
- Size and target filters are deterministic.
- Empty search results are represented as a normal result, not an exception.

### Integration Tests

- `usai rules list --source local-fixture` prints available rules.
- `usai rules search clean --source local-fixture` returns expected fixture rules.
- Non-cached source suggests update/download instead of failing with unclear file error.

### Acceptance Checks

- Search does not require AI or semantic embeddings.
- Source catalog output is stable enough for snapshot tests.

## Rules Installation And Update

### Unit Tests

- Rule file resolution by name and size works.
- Target directory resolution maps to `docs/rulesets/<target>`.
- Filename generation preserves readable rule names, for example `clean-code.nano.md`.
- Overwrite detection distinguishes same content from local modifications.

### Integration Tests

- `usai rules install clean-code --size nano --target always --source local-fixture` creates `docs/rulesets/always/clean-code.nano.md`.
- Reinstall without `--force` does not overwrite local edits.
- Reinstall with `--force` overwrites the installed file.
- `usai rules update --source local-fixture` updates cache only and does not rewrite project rulesets.
- Unknown rule name, unknown size and unknown target fail clearly.

### Acceptance Checks

- `rules update` never changes project files.
- Installing a rule prints the exact installed path.

- Paths use correct separators in output.
- Generated markdown is identical except for expected path formatting differences.
